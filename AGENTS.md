# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, Copilot, Cursor, Gemini CLI…) and humans.

## Project

`creep` is a model-agnostic CLI that finds vulnerabilities in local source code. Go, single binary, Apache-2.0.
Architecture (layers, contracts, maintainability decisions): [docs/architecture.md](docs/architecture.md). Package map: [docs/map.md](docs/map.md) (generated by `make map` once #120 lands) — read them instead of exploring.

## Commands

```sh
make check                        # all PR checks; run before every PR
make test PKG=./internal/<pkg>    # one package
make map                          # regenerate docs/map.md after adding/removing packages
go test ./... -failfast           # tests replay recorded model responses; no keys needed
```

## Invariants — never break these

1. Only `internal/gateway` may import `net/http` or open network connections. A linter enforces it.
2. Every model call goes through the gateway, which redacts secrets first and writes `egress.log`.
3. The planner receives only IDs, enums and booleans — never text from the scanned repo.
4. Model output is never executed on the host. PoCs run only in the sandbox (v0.2).
5. No telemetry. No network calls except to configured model endpoints.
6. No new direct dependency without an ADR in `docs/adr/`.

## Conventions

- Standard library first. Functions do one thing. Guard clauses over nesting. Files under 400 lines.
- Each package has a `doc.go` explaining why it exists.
- Errors wrap with context: `fmt.Errorf("redact %s: %w", path, err)`.
- Tests are table-driven. New behavior needs a test that covers its edge cases, failure paths and security protections, not trivial happy paths or getters; new model behavior needs a replay fixture. Engineering principles: [docs/architecture.md §8](docs/architecture.md#8-engineering-principles).
- Prompts live in `prompts/` as versioned data, one variant per model tier, with a token-budget test.
- Commits: Conventional Commits with `Signed-off-by` (`git commit -s`); SSH or GPG signing recommended (required once #49 lands).
- Test fixtures are generated in `t.TempDir()` unless they must be committed files; throwaway worktrees or folders go outside the repo and are removed when done.

## Workflow (spec-driven)

- **The GitHub issue is the spec**: context, scope, acceptance criteria. If the spec changes, edit the issue — do not add new `.md` files.
- **Agent loop (mandatory for every model-assisted change, enforced by `make budget`):** agents in order **developer → tester → pentester → auditor** ([ADR 0002](docs/adr/0002-agent-loop-scope.md), [ADR 0004](docs/adr/0004-pentester-per-release.md), [ADR 0005](docs/adr/0005-auditor-architecture-review.md)).
  - The developer implements the issue; the tester checks every acceptance criterion; the pentester does a static security review (no external network); the auditor re-rates each finding by real impact (exploitability, who can trigger it, existing mitigations) and posts its decision as a PR comment. The auditor also checks every PR against `docs/architecture.md` (layers, contracts, engineering principles, fitness functions) and reports each deviation as a finding rated by impact ([ADR 0005](docs/adr/0005-auditor-architecture-review.md)).
  - Developer, tester and auditor share context (issue, diff, test output, earlier verdicts). The pentester gets no shared context: only the issue, the diff and the repository, so its review stays independent.
  - The pentester runs once per version, over the whole version diff before the release is tagged, and on every pull request from an external contributor (anyone who is not a maintainer in CODEOWNERS). A confirmed Critical or High from the release pentest blocks the release; its fixes go through the normal loop. Alongside the release pentest, the auditor runs the per-version architecture review: the version diff against the principles and fitness functions, one issue per maintainability or scalability finding, and updated wiki Architecture diagrams (ADR 0005). The `security-sensitive` label, which only maintainers apply, marks what the release pentest must cover first. If the auditor sees security impact in an unlabeled change, it asks a maintainer to add the label so the release pentest covers it.
  - Confirmed Critical or High blocks the merge and goes back to the developer with the findings. Maximum 3 cycles, then escalate to the maintainer.
  - Medium, Low and Info do not block; each open finding becomes a follow-up issue.
  - Documentation-only changes run only the auditor (saves tokens): the PR touches only `*.md` files or `docs/`, and not code, workflows, settings, Makefile or the policy files (AGENTS.md, CLAUDE.md, CONTRIBUTING.md, PR template).
  - The auditor triages every open finding (audited severity, priority, size, milestone) and adds each follow-up issue to the project board (Roadmap, [sneakercreepers project 1](https://github.com/orgs/sneakercreepers/projects/1)) with those fields.
  - Changing or removing this loop needs an ADR in `docs/adr/` and maintainer approval; do not weaken it as a side effect of another change.
- Merge (squash) only when GitHub checks are green, the tester passes and the auditor allows it. Up to three features in flight at once, chosen from different packages or layers so they do not edit the same files ([ADR 0006](docs/adr/0006-three-features-in-flight.md)); each runs the full loop independently, and each branch is rebased on `main` and re-checked (CI green) before its squash merge.
- Branch `feat/<issue>-<slug>`; PR body `Closes #N`; labels from the issue.
- ADR only when a change adds a dependency or alters a public contract.
- After each merge, update **Current state** below (max 10 lines).
